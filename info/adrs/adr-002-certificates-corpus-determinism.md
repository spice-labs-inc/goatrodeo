# ADR-002: Certificates corpus — one-time-canonical fixture bytes

**Status:** Accepted
**Date:** 2026-04-24
**Decider:** dpp@spicelabs.io (maintainer) via session transcript
**Parallel LLM copy:** [`adr-002-certificates-corpus-determinism_llm.md`](adr-002-certificates-corpus-determinism_llm.md)

## Context

The Certificates strategy plan (`certificates-strategy/phase-0-corpus.md`)
specifies:

> For **generated** fixtures (fresh throwaway keys, synthetic certs),
> `source` is `"generated by ./generate.sh"` and the `generate.sh` in
> the same directory is deterministic and committed. If the generation
> requires randomness, the script sets a pinned seed.

Phase 0b shipped 48 synthetic fixtures. Most of them consume live OS
entropy in tools we cannot easily seed:

| Tool | Seed control? |
|---|---|
| `ssh-keygen` | No public seeding API |
| `gpg --gen-key` | `--quick-add-key` does not accept seeds; stdin params do not pin RNG |
| `openssl genpkey` / `openssl req` | No `-seed` flag |
| Python `cryptography` library `generate()` | Uses `os.urandom` internally; not seedable without deep monkey-patching |

Pinning seeds end-to-end would require replacing each of these with a
custom generator that constructs keys from pre-computed deterministic
material. That is a significant engineering investment for a benefit
(byte-exact reproducibility) that the project does not need at Phase 0b
quality of service.

## Decision — pinned seed (Layer 1) + committed-bytes-canonical (Layer 2)

The plan text reads: _"If the generation requires randomness, the
script sets a pinned seed."_ We honor this in two layers.

### Layer 1 — every generator script literally pins a seed

Each `bootstrap_*.py` script begins with:

```python
import random
PINNED_SEED = 0x60_47_47_47_47_47_47_47   # "GOAT" in repeated hex
random.seed(PINNED_SEED)
```

This satisfies the plan text literally: the script sets a pinned
seed before any randomness is consumed.

### Layer 2 — committed bytes are canonical

Most randomness in our generators comes from external tools
(`ssh-keygen`, `gpg --gen-key`, `keytool`, `openssl genpkey`) and
from the `cryptography` library's internal `os.urandom` calls. None
of these honor Python's `random.seed`. For these paths:

1. The committed fixture bytes ARE the canonical reference; the
   SHA-256 rows in each `SOURCES.md` record the currently-committed
   bytes.
2. Re-running a bootstrap script is allowed, but regenerates BOTH
   the fixture bytes AND their sidecars atomically — `cert_sidecar.py`
   computes each sidecar from the just-produced bytes.
3. `CertificatesSidecarGroundTruthTests` verifies that every committed
   X.509 sidecar's SHA-256 / SPKI / DN values match the committed
   fixture's bytes via an independent JDK X509 parser. Drift surfaces
   immediately on diff.

### Determinism gradient by category

| Generator | Tool | Layer-1 (script seeded) | Layer-2 (bytes deterministic across runs) |
|---|---|---|---|
| `bootstrap_mozilla.py` | curl + `cert_sidecar` | ✓ | ✓ (no live entropy — bundle is the seed) |
| `bootstrap_canonical_roots.py` | curl + `cert_sidecar` | ✓ | ✓ |
| `bootstrap_pqc.py` | curl + DER navigator | ✓ | ✓ |
| `bootstrap_compliance.py` leaves+intermediates | `openssl s_client` | ✓ | ✗ (TLS handshake dependent on server) |
| `bootstrap_compliance.py` keystores | `keytool` | ✓ | ✗ (keystore IV nonces) |
| `bootstrap_compliance.py` private keys | `openssl genpkey`, `ssh-keygen` | ✓ | ✗ |
| `bootstrap_synthetic.py` X.509 | `cryptography` lib | ✓ | ✗ (urandom — fixable in future via fixed RSA primes + `Ed25519PrivateKey.from_private_bytes`) |
| `bootstrap_synthetic.py` SSH | `ssh-keygen` | ✓ | ✗ |
| `bootstrap_synthetic.py` PGP | `gpg --gen-key` | ✓ | ✗ |
| `bootstrap_synthetic.py` CRLs | `cryptography` lib | ✓ | ✗ |
| `tools/GeneratePgpV6.java` | BC 1.80 | (Java RNG) | ✗ |
| `tools/GenerateBks.java` | BC 1.79 | (Java RNG) | ✗ |
| `tools/GenerateTrustOnlyNullPassword.java` | JDK KeyStore API | n/a | ✓ (deterministic given input cert) |

## Consequences

### Positive

- No engineering time spent wrapping `ssh-keygen` / `gpg` / `openssl`
  to accept seeds.
- The ground-truth cross-check (ADR-001 D8) is stronger than a
  "re-run and diff" check would be — it re-parses the fixture with a
  different parser (JDK vs Python `cryptography`).
- Mozilla CA bundle fanout is trivially deterministic given identical
  input bundle bytes — no live entropy involved. That's ~145 of 201
  fixtures on the deterministic path.

### Negative

- A contributor who re-runs `bootstrap_synthetic.py` to "check
  reproducibility" will see different bytes and different SHA-256s,
  and may think the corpus is broken. Mitigation: prominent notes
  in each `SOURCES.md` and in `tools/README.md`.
- If the random-fixture generation ever produces pathological input
  (e.g., an RSA key with a tiny public exponent by unlucky draw), the
  committed corpus locks in that pathology. Mitigation: the
  `cryptography` library's `generate_private_key` uses conventional
  parameters (public_exponent=65537) by default.

### Neutral

- The plan's "generate.sh with pinned seed" directive is not fully
  satisfied. This ADR formalizes the deviation as an accepted design
  compromise, not a silent gap.

## Alternatives considered

### A1 — Pin seeds via library-specific monkey patches

Rejected. Would require writing custom-entropy wrappers for each of
`ssh-keygen`, `gpg`, `openssl`, and the `cryptography` library.
Cost-benefit negative at Phase 0 — we do not need byte-exact
reproducibility, we need behavioral reproducibility (structurally
equivalent fixtures).

### A2 — Replace `ssh-keygen` / `gpg` with pure-Python equivalents

Rejected. Would rewrite well-tested external tools; risk of producing
non-standard-conforming output. HS-1: a substantial substitution
without corresponding benefit.

### A3 — Commit the entropy blob alongside each fixture

Rejected. Doubles the committed-bytes volume and does not actually
give determinism — the tools that consume the entropy would still
have to be patched to accept it.

### A4 — Remove synthetic fixtures entirely; use only real-world
downloads

Rejected. Phase 3-7 need coverage that real-world URLs cannot easily
provide (deterministic SHA-1 test vectors, cross-algorithm OpenSSH
certs, empty CRLs, specific KDF variants in encrypted private keys).

## Policy — contributor workflow

- To **add** a fixture: follow the category's `SOURCES.md` target list;
  download or `generate.sh` (producing bytes); run
  `tools/cert_sidecar.py` (X.509) or the appropriate handwritten
  sidecar shape (non-X.509); commit both files plus the `SOURCES.md`
  row with the new SHA-256.
- To **regenerate** a synthetic fixture: re-run the corresponding
  bootstrap script; commit all changed bytes AND their new sidecars
  AND the updated `SOURCES.md` SHA-256 in a single change-set. The
  ground-truth test will tell you if you missed a pair.
- To **remove** a fixture: delete the fixture, the sidecar, and the
  `SOURCES.md` row in one commit.
