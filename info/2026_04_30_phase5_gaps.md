## G1 — `valid_before = 0xFFFFFFFFFFFFFFFF` ("never expires") wraps to 1969-12-31 (CRITICAL bug)

**Severity:** Real correctness bug. Not caught by any test.

`SshCert.validBefore: Long` is read via `SshWireReader.readUInt64()`, which returns the unsigned 64-bit value cast to `Long`. The OpenSSH convention for "never expires" — emitted by `ssh-keygen -V always:forever` and common in long-lived host keys — is `0xFFFFFFFFFFFFFFFFL`. As `Long` this becomes `-1L`, and `Instant.ofEpochSecond(-1)` yields `1969-12-31T23:59:59Z`. The strategy then emits a metadata claim that a never-expiring cert is already expired by 57 years.

Symmetrically, `valid_after == 0` is the "always" sentinel; rendering it as `1970-01-01T00:00:00Z` is *technically* correct but obscures intent.

**Why no test catches it:** all 6 cert fixtures in `test_data/certificates/ssh/synthetic/` use bounded `-V +52w` validity (verified via `ssh-keygen -L`); zero use the sentinel. Property-based tests would have surfaced this.

**Remediation:** in `sshCertMetadata`, detect `c.validBefore == -1L` (unsigned max) and `c.validAfter == 0L` and either omit the field or emit a literal token (`"forever"` / `"always"`). Add a unit test against a hand-crafted cert blob with the sentinel bytes. Add a corpus fixture generated with `-V always:forever`.

**Severity:** Plan-conformance violation.

Phase 5 plan, fixture table (lines 125-135 of `certificates-strategy/phases-5-7-ssh-pgp-private.md`):

- `sk-ed25519.pub` — "include a manually-crafted test vector" (security-key variant)

The "non-empty list emits comma-separated names" branch is dead in regression.

**Remediation:** generate / hand-craft both fixtures. Minimum acceptable: regenerate one existing cert with `-O force-command=…` AND add a unit test in `SshStrategyParserTests` that builds an `SshCert` instance with non-empty `criticalOptions` and asserts the metadata emission.

## G4 — Five `sshAlgMap` entries have zero corpus coverage; `sk=true` qualifier path is dead

**Severity:** Dead-code risk; HS-3 weakness.

`Certificates.sshAlgMap` declares 9 wire-name entries matching the plan. Per-fixture tests cover 4 plain types — `ssh-rsa`, `ssh-ed25519`, `ecdsa-sha2-nistp256`, `ecdsa-sha2-nistp384`. The remaining 5 entries — `ssh-dss`, `ssh-ed448`, `ecdsa-sha2-nistp521`, `sk-ssh-ed25519@openssh.com`, `sk-ecdsa-sha2-nistp256@openssh.com` — have **no fixture exercising them in `CertificatesSuite`**.

Concretely:

- The `sk=true` branch of `sshKeyQualifiers` is never executed by green tests. A bug that emitted `sk=true` always (or never) would not fail.
- The `Certificates:SshIsSecurityKey` metadata key is never emitted. A regression that mis-typed it as `SshIsSecuritKey` would pass.
- The `signedKeyAlgFromCertName` suffix-strip logic for `sk-*-cert-v01@openssh.com` (which OpenSSH does support) is untested.

**Remediation:** for algorithms that can be generated locally (Ed448 on recent OpenSSH, ECDSA-P521, DSA on legacy OpenSSH), add corpus fixtures. For `sk-*` variants (require security keys), follow the plan's "manually-crafted test vector" guidance and add a parser unit test against hand-built wire blobs in `SshStrategyParserTests`.

## G5 — Zero property-based tests; CLAUDE.md inv #1 deferral lacks HS-1 approval

**Severity:** CLAUDE.md inv #1 / HS-1.

CLAUDE.md inv #1: "have substantial property-based tests".

Phase 5 ships zero property-based tests. The Phase 5 plan defers property testing to Phase 8. My `phase-5-claims.md` lists this under "Out-of-scope items (by design)" — but I never invoked HS-1 to ask the user whether the deferral was acceptable. That is the deviation HS-1 is written to prevent.

**Properties whose absence creates real risk:**

1. *Wire round-trip*: for any well-formed SSH wire blob `w`, `parseSshPubkey(write(w))` returns `Some(p)` such that `p.wireBytes ≡ w`.
2. *Fingerprint stability under cosmetic noise*: prepending whitespace, BOM, or trailing newlines to the input file does not change the emitted `pkg:ssh/sha256@…` fingerprint.
3. *Cert-vs-pubkey disjointness*: for any file whose first whitespace-token ends in `-cert-v01@openssh.com`, `parseSshPubkey` returns `None`; for any file whose first token is in `sshPubkeyTokens \ sshCertTokens`, `parseSshCert` returns `None`.
4. *Boundary read*: for any `(byte_array, offset)` with `offset > byte_array.length - 4`, `SshWireReader(byte_array.drop(0)).readUInt32()` throws.
5. *mpint round-trip*: `mpintBitLength(write_mpint(BigInt(n))) == n.bitLength` for any non-negative `n`.

Property #4 in particular guards against the "silently truncate or wrap" failure mode that produced bug G1.

**Remediation:** add ScalaCheck property tests for at least #1, #4, #5 in this phase, OR explicitly surface the deferral and obtain user approval per HS-1.

## G6 — Cert sidecars assert ≤ 2 of ~12 metadata fields (HS-3 coverage hole)

**Severity:** Test coverage hole.

Inspection of all 6 materialized cert sidecars (`info` directory shows the strategy emits ~12 SSH-cert metadata keys: `Certificates:KeyAlgorithm`, `SshFingerprintSha256`, `SshCertSha256`, `SshCertType`, `SshCertSerial`, `SshCertKeyId`, `SshCertValidAfter`, `SshCertValidBefore`, `SshCertCaFingerprint`, `SshCertSigAlgorithm`, optional `SshCertPrincipals`, `SshCertExtensions`, `SshCertCriticalOptions`, `SshComment`). Every cert sidecar's `metadata.mustContain` declares only `SshCertType` plus (optionally) `SshCertPrincipals`. The remaining 10+ fields are **un-asserted by any per-fixture test**.

Concrete blast radius:

- A regression that emits the wrong `SshCertCaFingerprint` (e.g., uses the signed-key wire instead of the CA-key wire) passes all tests. Critical for security correctness.
- A regression that mis-formats `SshCertSerial` (decimal vs hex) passes all tests.
- A regression that sets `SshCertSha256` to the signed-key fingerprint instead of the cert SHA-256 passes all tests.
- The G1 bug above would produce wrong `SshCertValidAfter`/`SshCertValidBefore` and pass all per-fixture tests.

The materializer's metadata-placeholder logic only fills `<computed>` placeholders; it does not *add* assertions for fields the sidecar didn't pre-declare. So fields the original sidecar omitted stay un-asserted forever.

**Remediation:** extend the sidecars to assert the full metadata table for at least one reference fixture per cert variant (Ed25519 user, RSA host signed by Ed25519, ECDSA-P256 user). The values can be materialized from the strategy itself (same tautology pattern as Phase 4) — but with a property: an independent script reads the cert via `ssh-keygen -L` and cross-checks the materialized values against the OpenSSH ground truth.

## G7 — `parseFirstKeyLine` silently misses `authorized_keys` option-prefixed lines

**Severity:** Plan-scope question / real-world parsing gap.

Real-world `authorized_keys` lines often have options before the algorithm token:

```
from="1.2.3.4",no-pty,command="/bin/echo" ssh-rsa AAAAB3Nz... user@host
```

`parseFirstKeyLine` splits on whitespace and treats the first token as the algorithm name. With options first, the first token is `from="1.2.3.4",no-pty,…` which fails both the detector's `sshPubkeyTokens.contains` check and the strategy's algorithm lookup. The artifact is silently never claimed and never parsed. No log message, no warning.

The Phase 5 plan describes "single-line OpenSSH wire format" not authorized_keys. A strict reading is "out of scope". A pessimistic reading (HS-3) is that real-world deployments will hit this, and a silent miss in a crypto inventory tool is the wrong failure mode.

**Remediation (pick one):**

- (a) Extend `parseFirstKeyLine` to scan tokens left-to-right for the first token matching a recognized algorithm name (passes Phase 5 plan strictness; handles the real world).
- (b) Document the limitation explicitly in `phase-5-claims.md` and the strategy doc; add a fixture under `ssh/edge-cases/` and an explicit assertion that it's not claimed.
- (c) HS-1: surface and ask.
